# `dasho.StringDecrypt`:通解字符串还原 pass 的设计

本文是本仓第一个 pass 的实现说明:**为什么不按形态匹配**、两条改写策略如何分工、以及每条不变量的来源。技术形态本身见 [string-encryption.md](string-encryption.md)。

## 1. 设计立场:求值,而不是匹配

DashO 的调用点形态族谱有六七维(有无谓词、极性、key 位置、签名、解密器名字、层数、是否有异常表)。逐维写匹配规则会得到一个指数级的判据树,而且每一维都随构建随机——规则一旦写死,下一次构建就可能失效。

本 pass 的判据只有一条:**这个调用点是纯的、可静态求值的常量表达式**。于是:

| 环节 | 做法 | 不做什么 |
|---|---|---|
| 找锚点 | 返回 String 的 `invokestatic`,callee 纯度可判定 | 不认名字、不认类名、不认签名 |
| 定区间 | 从锚点往前找最早的"空栈起算仍恰好产出 1 个值"的连续指令段 | 不识别谓词形状、不识别 key 算术形状 |
| 求值 | 小型字节码解释器执行区间,多 `Random` 种子结果须一致 | 不做代数化简、不识别 `(r*N)%r` |
| 改写 | 区间 → 一条 `ldc 明文` | 不重建解密算法 |

代价是:需要一个能跑纯字节码的解释器(`jvm_interp.cpp`),而不是几十行模式匹配。收益是:形态族谱的每一维都不需要写代码。

## 2. 区间为什么能"自己长对"

锚点的实参由区间内的指令压入。DashO 把「外层 key 算术 + 谓词 + 双支 + 密文 ldc + 伪内层解密」全部放在锚点之前,并且这段的净栈效应恰好是 `+1`(一个 String)。于是:

- 从锚点往前退,第一个满足"空栈起算净效应 +1"的位置,就是这段表达式的最左端;
- 中间那些分支、死支、诱饵 ldc 全在区间内,**不需要理解它们**——解释器只走实际执行的那条路径;
- 死支里的指令从未执行,但它们**在区间内**,所以整段折叠时会被一并删除(见 §3)。

`structurallyOk` 的约束是必要的:区间外不得跳入区间内部(否则"这段是自洽的常量表达式"不成立),异常表边界不得落在区间内部(否则折叠会改变保护范围)。

## 3. 两条改写策略

「指令增删」和「帧是否还能用」是两件事,必须分开处理。

### 3.1 整段折叠(方法**无**异常表)

区间除头指令外全部擦除,头指令改写为 `ldc 明文`。

- 死支诱饵一并消失 —— 这是最干净的产物。
- 指令增删 ⇒ 既有 StackMapTable 的帧目标悬垂 ⇒ 写回时按新布局**再生**帧。
- 前置条件:死支(未执行的指令)必须是可擦除形态(`erasableOp`);区间内写过的局部变量不得在区间外被读(`localsNotEscaping`)。

### 3.2 原地改写(方法**有**异常表)

只做两件事:密文 `ldc` 换成明文;解密调用换成等价的**收栈序列**。指令数与栈形不变,死支诱饵留在原地。

为什么不能整段折叠:带异常表的方法里,既有 StackMapTable 含 verifier 要求的**保守 handler 帧**——handler 的 locals 必须是 try 区间内**每条**指令处 locals 的合并(未定值的位置取 `top`)。libjbc 的 Strict 域只从 `canThrow(op)` 为真的指令发异常边,比 verifier 精确;按它重算出的 handler 帧与 verifier 的期望不一致,写回即 `VerifyError`。原地改写不改栈形,原帧逐条仍然成立,由 lower 的 relocation 精确搬运——**不需要也不可能安全地重算**。

代价是死支诱饵留在原地(不可达,但仍是可见噪声)。这是一次明确的取舍:正确性优先于产物洁净度。

### 3.3 收栈序列怎么来

密文是实参之一,结果是"只留密文、弹掉其余实参"。序列由**实参栈**推出,不猜签名:

| 描述符 | 栈(底→顶) | 序列 |
|---|---|---|
| `(String)` | `[ct]` | `nop`(调用本身就是恒等) |
| `(String,int)` | `[ct, k]` | `pop` |
| `(String,int,int)` | `[ct, k1, k2]` | `pop; pop` |
| `(int,String)` | `[k, ct]` | `swap; pop` |
| `(String,String)` | `[k, ct]` | `swap; pop` |

通用式:密文位置 `p`、实参个数 `n` ⇒ 上方 `n-1-p` 个逐个 `pop`,下方 `p` 个逐个 `swap; pop`。全 cat-1 才成立(`swap` 对 cat-2 无定义),cat-2 直接放弃。

实参栈通过"跑 `[start, anchor)` 区间"取得。这里有个坑:`ifeq` 模板的活动支常以 `goto 锚点` 收尾,锚点正好在区间外一格——严格越界判定会把这种形态判失败。所以 `runRegion` 增加了一个 `exitOk` 参数:控制流转移到该指令即视为区间正常结束。

### 3.4 两个独立信号的交叉校验

"哪个实参是密文"由两个独立信号确认,一致才动手:

1. **字节码来源**:区间内最后一条**已执行**的 String `ldc`(DashO 把密文放在实参最外侧,故它是最后一个被压入的字符串);
2. **运行期栈**:该 `ldc` 的文本在实参栈中的位置**唯一**,且描述符在同位置声明为 String。

不一致 ⇒ 不是可安全改写的形态 ⇒ 跳过。这条闸挡住了 `(String,String)` 里"key 在前、密文在后"与"密文在前"的歧义。

### 3.5 栈深一致性

收栈序列按"实参槽数"生成,只有当**每条**路径到达锚点时栈深一致,这个序列才在每条路径上都成立。DashO 的双支模板两支各压 1 个值,天然满足;非对称分支则不然。

`anchorDepthUniform` 用一张栈效应表(`stackDelta`)在区间内做栈深 DFS,要求到达锚点的深度唯一且等于实参槽数。不满足就跳过——退化为"不改",而不是产出坏字节码。

## 4. 锚点扫描顺序:最外层优先

嵌套调用 `f(g(x))` 里,外层的 `invokestatic` 一定在内层之后。若先折内层,内层的收栈序列会把实参压成 1 个值,而外层区域仍按"原始实参个数"改写——两条路径的栈深不一致,产物必然 `VerifyError`。

因此 `run()` **倒序扫描锚点**。先折外层,内层作为区域的一部分被常量折叠吸收,不存在嵌套残留。

注意:原地改写不擦除死支,所以死支里的"伪内层解密"会在后续轮次里被单独折叠。这是**无害且有益**的——净栈效应不变、纯方法无副作用,而且折掉之后即使解密器类被移除也不会留下悬垂调用。

## 5. 纯度判定的边界

`ClassSet::isPure` 拒绝:字段读写、`monitorenter/exit`、`athrow`、`invokedynamic`、`jsr/ret`、native/abstract/synchronized;调用面必须是 JDK 内建纯方法(`isIntrinsicCall`)或递归纯方法(带环检测,环 → 不纯)。

这条判定的作用是**保证求值不改变语义**:解释器只在纯方法上递归,绝不执行有副作用的代码。它也是唯一的"信任边界"——判错了就会执行用户代码。所以宁可判窄(拒绝)不可判宽(接受)。

## 6. 写回链

`ClassSet::commit` 按方法粒度处理:

| 方法 | lower 前 | lower 后 |
|---|---|---|
| `structural = true` | `prepareNestedAttrsForLayout`(把 LNT/LVT/SMT 适配到可重定位形态,悬垂 SMT 摘除) | 帧链再生:Strict 重算 → `applyComputedMaxes` → 二次 lower 落 maxes → `buildStackMapTable` 挂回 |
| `structural = false` | — | 不重算;布局变化(如 `LDC`→`LDC_W`)由 lower 的 relocation 精确搬运 |

`structural` 只在整段折叠时置真。原地改写的插入保持"帧目标 ↔ 指令句柄"绑定,relocation 已足够——重算反而会引入与 verifier 保守合并不一致的 handler 帧(§3.2)。

## 7. 死解密器清扫

调用点全部折叠之后,DashO 生成的解密器类(`Owner$1`)通常就没有调用者了。留着它们,还原产物里会凭空多出几个匿名类,反编译时还得逐个判断"这是不是业务代码"。

### 7.1 为什么不能只数常量池

libjbc 的常量池**只追加**:折叠把 `invokestatic` 换成 `ldc` 之后,那条 `Methodref` 和它指向的 `Class` 条目仍留在池里。按 CP 条目数引用,结论永远是"还有引用",一个也删不掉(实测确实如此)。

所以判定分两步:

1. **预筛**(便宜):该类 CP 里是否出现候选类名;没有则必然无关。
2. **定判**(精确):在预筛命中的类里逐方法看**活指令**——`classOf`(`new`/`checkcast`/`anewarray`/`instanceof`/`multianewarray`)、`memberOf`(invoke/get/put 的 owner)、`constOf`(`ldc` 的 Class 常量)、异常表 `catch_type`、类头 `super`/`interfaces`、成员声明描述符。

任一步解不开(方法体 promote 失败)就**整体放弃清扫**:宁可留残留,不可删活类。

### 7.2 候选从哪来

两类取并集:

- **锚点指向过的类**:折叠时解析到的 callee owner;
- **形态上就是解密器的类**:类名 `<Owner>$<数字>` + 无字段 + 无 `<init>` + 全部方法 `static` + 至少一个返回 `String`。

第二类补上了第一类的漏网。DashO 的"双支"结构里可能把对另一个解密器的调用塞进死支,整段折叠时随区间一起被擦掉——那个解密器**从未当过锚点**,但此刻同样已经没有调用者了(实测 `DataOfSquare$1` 即此情形)。

### 7.3 已知不覆盖

反射按名字加载(`Class.forName("Owner$1")` 是字符串常量)、`META-INF/services` 里的文本引用——这两类都只会导致"该删没删",方向安全。

## 8. 失败面

每一步不成立都退化为"跳过该站点",不做猜测性改写。`DASHO_TRACE=1` 会把站点级拒绝原因打到 stderr(诊断用,平时零开销)。

| 拒绝原因 | 含义 |
|---|---|
| 区间求值失败或多 seed 不一致 | 不是常量表达式,或依赖随机源 |
| 明文不合法 | 求值产物含 NUL/孤立代理项/C0-C1 控制符 |
| 实参个数与描述符不符 | 区间端点选错(通常是非自洽形态) |
| 密文常量在实参栈中不唯一 | 无法确定哪一位是密文 |
| 密文位置在描述符中不是 String | 两个信号矛盾 |
| 锚点栈深不一致 / 与实参槽数不符 | 非对称分支,收栈序列不安全 |
| 区间内无已执行的 String ldc | 锚点实参与区间不对应 |

## 9. 单测与回归

- **单测**(`test/unittest/string_decrypt_pass_test.cpp`,11 例):夹具手工拼形态 A / 形态 B(两种极性)/ 带异常表 / 三种收栈形态 / custom SE / 嵌套 / 不纯解密器 / 解密器不在 jar 内 / 非法明文。断言的是**改写形状**(指令序列),不是明文内容——解密算法正确性由回归覆盖。
- **回归**:26 个样本 jar 全跑 + JDK 校验器全绿;形态覆盖表见 [string-encryption.md](string-encryption.md) §7。

> 夹具踩过的坑值得记一笔:**JVM 分支偏移是相对分支指令自身的 pc**(JVMS 6.5),不是相对下一条指令。按"下一条"算出来的 `goto` 会变成自环(解释器报 `StepLimit`),或落在指令中间(报 `BadTarget`)。
